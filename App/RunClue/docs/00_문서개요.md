# RunClue 프로젝트 문서 개요

## 1. 프로젝트 소개

RunClue는 **참여형 미션 플랫폼**으로, 사용자가 오프라인 활동, 온라인 퀴즈, 생활 도움 요청, 교육 확인 등 다양한 목적의 미션("Clue")을 직접 설계하고 참여할 수 있는 서비스이다.

### 1.1 핵심 가치

| 가치 | 설명 |
|------|------|
| 참여 중심 | 누구나 Clue를 만들고 참여할 수 있는 양방향 구조 |
| 현실 연결 | 오프라인 활동과 디지털 검증을 결합 |
| 유연한 설계 | Step 조합으로 무한한 미션 시나리오 구성 가능 |
| 신뢰 기반 | 자동/지연/수동 검증을 통한 공정한 증거 확인 |
| 보상 다양성 | 포인트, 뱃지, 쿠폰, 경품, 추첨권 등 복합 보상 체계 |

### 1.2 주요 활용 시나리오

- **오프라인 활동**: 숨바꼭질, 보물찾기, 대학 MT, 수학여행, 기업 워크숍
- **온라인 퀴즈**: 퀴즈 대회, 스트리머 방송 연동
- **생활 도움**: 벌레 잡기, 분실물 찾기 등 일상 요청
- **교육 확인**: 출석 체크, 현장 실습 평가
- **지역 상권**: 로컬 비즈니스 프로모션, 상점 스탬프 투어

## 3. 통합 용어 정의

모든 문서에서 아래 용어를 통일하여 사용한다.

### 3.1 핵심 도메인 용어

| 용어 (한글) | 용어 (영문) | 정의 |
|-------------|-------------|------|
| 클루 | Clue | 게임/이벤트/요청의 단위. 하나 이상의 Step으로 구성되며, 참여 조건, 검증 방식, 보상을 포함한다. |
| 스텝 | Step | Clue 내부의 개별 단계. 유형에 따라 참여자가 수행해야 할 행동이 달라진다. |
| 증거 | Evidence | Step 완료를 입증하기 위해 참여자가 제출하는 자료. 사진, 위치, 영상, QR, 답변, 텍스트 등의 형태를 가진다. |
| 검증 | Validation | 제출된 증거가 유효한지 확인하는 절차. 자동(auto), 지연(delayed), 수동(manual) 방식이 있다. |
| 보상 | Reward | Clue 또는 Step 완료 시 참여자에게 지급되는 대가. 포인트, 뱃지, 쿠폰, 경품, 추첨권 등이 있다. |
| 제작자 | Creator | Clue를 설계하고 생성하는 사용자. |
| 참여자 | Participant | Clue에 참여하여 Step을 수행하는 사용자. |
| 클랜 | Clan | 사용자들이 구성하는 그룹/팀 단위. Clue에 팀 단위로 참여하거나 커뮤니티 활동을 할 수 있다. |

### 3.2 Step 유형

| 유형 | 영문 코드 | 설명 |
|------|-----------|------|
| 체크포인트 | CHECKPOINT | 특정 위치에 도달하여 GPS 또는 QR로 인증하는 단계 |
| 스냅샷 | SNAPSHOT | 사진 또는 영상을 촬영하여 제출하는 단계 |
| 퀘스트 | QUEST | 주어진 미션(텍스트 기반 과제)을 수행하고 결과를 제출하는 단계 |
| OX 퀴즈 | OX_QUIZ | O/X 또는 객관식 문제에 답하는 단계 |
| 리스트 | LIST | 여러 항목을 수집하거나 체크리스트를 완료하는 단계 |
| 게시판 | BOARD | 게시판에 글을 작성하거나 댓글을 남기는 단계 |
| 파노라마 | PANORAMA | 360도 또는 파노라마 사진을 촬영하여 제출하는 단계 |
| 안면 인식 | FACIAL | 얼굴 인식을 통해 본인 확인 또는 출석을 인증하는 단계 |

### 3.3 검증 방식

| 방식 | 영문 코드 | 설명 |
|------|-----------|------|
| 자동 검증 | AUTO | 시스템이 즉시 자동으로 증거를 판별한다 (GPS 범위, QR 일치, 정답 비교 등). |
| 지연 검증 | DELAYED | 일정 시간 후 자동 검증되거나, 조건 충족 시 일괄 검증된다. |
| 수동 검증 | MANUAL | 제작자 또는 관리자가 직접 증거를 확인하고 승인/반려한다. |

### 3.4 보상 유형

| 유형 | 설명 |
|------|------|
| 포인트 | 플랫폼 내 적립 가능한 디지털 포인트 |
| 뱃지 | 특정 업적 달성 시 부여되는 디지털 배지 |
| 쿠폰 | 제휴 업체 또는 플랫폼에서 사용할 수 있는 할인/교환권 |
| 경품 | 실물 또는 디지털 상품 (선착순 또는 조건부 지급) |
| 추첨권 | 추첨을 통해 당첨 시 경품을 받을 수 있는 응모권 |

### 3.5 사용자 역할

| 역할 | 설명 |
|------|------|
| 비회원 (Guest) | 앱 설치 후 가입 전 상태. Clue 탐색만 가능하다. |
| 일반 회원 (Member) | 가입 완료 사용자. Clue 참여 및 기본 제작이 가능하다. |
| 인증 제작자 (Verified Creator) | 본인 인증을 완료한 제작자. 유료 Clue 및 고급 기능을 사용할 수 있다. |
| 클랜장 (Clan Leader) | 클랜을 생성하고 관리하는 사용자. |
| 운영자 (Admin) | 플랫폼 전체를 관리하는 관리자. 신고 처리, 컨텐츠 검수 권한을 가진다. |

### 3.6 Clue 상태

| 상태 | 영문 코드 | 설명 |
|------|-----------|------|
| 초안 | DRAFT | 제작 중인 상태. 공개되지 않는다. |
| 검수 대기 | PENDING_REVIEW | 제작 완료 후 운영 검수를 기다리는 상태. |
| 승인 | APPROVED | 검수 통과. 공개 가능 상태. |
| 진행 중 | ACTIVE | 현재 참여 가능한 상태. |
| 마감 | CLOSED | 참여 기한 또는 인원이 마감된 상태. |
| 종료 | COMPLETED | 모든 보상 지급이 완료된 상태. |
| 반려 | REJECTED | 검수에서 반려된 상태. 사유가 제작자에게 전달된다. |
| 신고 정지 | SUSPENDED | 신고 누적 또는 운영 판단으로 정지된 상태. |

## 4. 설계 원칙

### 4.1 제품 설계 원칙

1. **모바일 퍼스트**: 모든 화면과 기능은 모바일 환경을 최우선으로 설계한다.
2. **3탭 이내 도달**: 핵심 기능은 최대 3번의 탭(터치) 이내에 접근할 수 있어야 한다.
3. **오프라인 내성**: 네트워크 불안정 환경에서도 증거 제출이 유실되지 않도록 로컬 저장 후 재전송 구조를 적용한다.
4. **점진적 공개**: 복잡한 제작 기능은 기본 모드와 고급 모드로 분리하여 진입 장벽을 낮춘다.
5. **신뢰 우선**: 증거 위변조 방지, 개인정보 보호, 투명한 보상 정산을 설계의 기본으로 삼는다.
6. **접근성 준수**: WCAG 2.1 AA 수준의 접근성을 목표로 한다.

### 4.2 기술 설계 원칙

1. **API 우선 설계**: 모든 기능은 API를 먼저 정의하고, 클라이언트는 API를 소비하는 구조로 개발한다.
2. **이벤트 기반 아키텍처**: 검증, 보상, 알림 등 비동기 처리가 필요한 영역은 이벤트 기반으로 설계한다.
3. **확장 가능한 Step 구조**: 새로운 Step 유형을 플러그인 방식으로 추가할 수 있도록 설계한다.
4. **데이터 최소 수집**: 기능 구현에 필요한 최소한의 개인정보만 수집하고, 보관 기간을 명시한다.
5. **멱등성 보장**: 보상 지급, 증거 제출 등 중요 API는 멱등성을 보장한다.

## 5. 문서 규칙

### 5.1 문서 작성 규칙

- 모든 문서는 **한국어**로 작성한다.
- 기술 용어, 코드명, API 경로 등은 **영문 원문**을 병기한다.
- 테이블의 열 이름은 한글로 표기하되, 코드에 직접 매핑되는 값은 영문으로 표기한다.
- 각 문서는 독립적으로 읽을 수 있되, 용어 정의는 본 문서(00번)를 기준으로 통일한다.

### 5.2 상태 표기 규칙

- 구현 상태: `[미정]`, `[확정]`, `[구현중]`, `[완료]`, `[보류]`
- 우선순위: `P0(필수)`, `P1(높음)`, `P2(보통)`, `P3(낮음)`
- 변경 이력은 각 문서 하단에 테이블로 관리한다.

### 5.3 ID 체계

|------|--------|------|
| 화면 | SCR- | SCR-001 |

| API | API- | API-001 |
