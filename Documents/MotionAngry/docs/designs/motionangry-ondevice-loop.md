## Problem Statement
폰이 사용자가 콘텐츠(멜론 음악, 유튜브·인스타 영상)를 소비하는 동안 "지금 좋아하네/별로네"를 움직임 센서와 표정 계수로 단말 안에서 읽고, 그 즉시 반응 타임라인·자동 좋아요/스킵·"맞아요?" 확인·반응 스탬프로 돌려주는 시스템. 사용자 최종 목표: "전체적인 콘텐츠·소비 피드백을 즉각적으로 받을 수 있게끔 하는 스마트 온디바이스 시스템".

지금까지의 실험이 말하는 것:
- 일상 각성은 손목 움직임 세기·저크로 AUROC 0.62까지만 나오고, 측정 빈도·모델 크기·개인 기준선 보정·자기 응답 30개 누적(S4·S6·S7) 어느 것도 **사용자 안** 판별을 올리지 못했다.
- 실기록 7시간: 표정은 폰을 들고 볼 때만 잡히고(음악 앱 12~32%, 영상·SNS 44~79%), 움직임은 항상 있다. 웃음↔저주파(0~3Hz) 가속도 ρ=0.32·자이로 0.29, 64쌍 보정 후 8쌍 유의.
- 단말 파이프라인은 Python과 1e-15로 일치, 1분 단계 0.22ms, 추정 0.26ms, 모델 7.5KB.

따라서 풀 문제는 "단말이 **스스로 모은 풍부한 정답**(표정 계수·감정 격자·맞아요/아니에요)으로, 데이터를 밖으로 내보내지 않고, 그 사람 안의 변화를 읽게 되는가"다. (docs/evolve_loop.md 문제 정의 v3. 반복마다 갱신.)

## What Makes This Cool
- **표정이 보일 때 배워서, 안 보일 때 움직임만으로 읽는다.** 검색(2026-10-24)에서 폰 정서 연구는 카메라 표정(ARKit 68%) 아니면 손목 심박·피부전도였고, 가속도는 활동 인식에만 쓰였다. 표정을 선생님으로 써서 그 사람의 움직임 모델을 단말에서 가르치는 교차 모달 자기지도 개인화는 비어 있는 자리다.
- **정답을 색으로 받는다.** Affect Grid(Russell 1989)를 연속 색 격자로 만들어 한 번 누르면 정서가·각성·세기·감정 이름이 한꺼번에 기록된다. K-EmoPhone과 같은 축이라 공개 데이터와 자기 데이터가 바로 비교된다.
- **부정 결과가 설계를 정당화한다.** "자기 응답을 쌓아도 사용자 안 판별은 안 는다"(S7)가 왜 라벨을 바꿔야 하는지, 왜 온디바이스여야 하는지를 한 줄로 설명한다.

## Constraints
- 1인 연구, 참가자 모집 불가 → 공개 데이터(K-EmoPhone·WESAD·StudentLife, 입수 예정: 간호사 E4·DAPPER) + 본인 N-of-1 + 친구 3~5명 APK.
- 기기: 갤럭시 노트9(Android 10, 가속도 HW FIFO 3,000이벤트, 자이로 FIFO 없음), ESP32 보유, IMU 모듈 구매 가능.
- 앱은 INTERNET 권한 없음. 원시 신호·표정 계수는 단말 밖으로 안 나간다.
- 상시 기록 원칙(조건부·이벤트 기반 수집 제안 금지, 사용자 2026-10-09).
- 마감: 단기 학회 제출 2026-10-25(토). KCI는 그 뒤. 교수님 요구: 온디바이스 구현 + 칩셋·모델 경량화.
- 디자인: 이모지 금지, AI 티 없는 화면(사용자 취향 메모).

## Premises
1. 병목은 신호가 아니라 라벨이다 — 빈도·모델 크기·응답 누적으로는 사용자 안 판별이 안 올랐다(S4·S6·S7).
2. 표정은 정답이 아니라 선생님이다 — 최종 추정은 카메라 없이 움직임만으로 나와야 한다(폰 내려둔 음악 듣기). 교사(폰 든 상태)와 학생(폰 내려둔 상태)의 도메인 이동은 폰 자세로 나눠 **측정**한다.
3. (2차 의견으로 수정) 평가는 "같은 사람의 나중 데이터에서 출하 모델 대비 개선폭"이고, 정답은 격자 탭·맞아요/아니에요다. 단 질문 알림은 **급변 트리거 팔(A)과 같은 횟수의 무작위 시각 팔(B)**로 나누고, 개선 주장은 B에서만 한다. A와 B의 일치율 차이는 "모델이 자신 있을 때 얼마나 더 맞나"라는 보조 결과.
4. 온디바이스는 전제다 — 이 학습은 단말에서만 가능하고, 그것이 칩셋·경량화 절의 이유다.

## Cross-Model Perspective
(Claude 서브에이전트 cold read, 이 대화를 보지 않음. Codex는 Bun 크래시로 불가.)
- 가장 멋진 버전: **비트 동조 지수** — 좋아한 곡에서 0~3Hz가 늘고 웃음이 저주파와 상관인 것은 몸이 박자에 잠기는 현상일 수 있다. Visualizer로 출력 오디오 온셋·템포를 뽑아 IMU 0~3Hz와 위상 코히어런스를 재면 라벨 없는 연속 지표가 된다. 대가는 음악으로 범위 축소.
- 핵심 주장: "blending raises pooled AUROC but within-user AUROC does not improve" — 긍정 수치(0.62·7.5KB·0.26ms)는 부차적이고 이 부정 결과가 '왜 단말이 스스로 정답을 모아야 하나'를 정당화한다. 손목 8Hz에서 나온 결과이므로 폰 IMU 일반화는 한계로.
- 50%: LiteRT(TFLite) On-Device Training의 공식 `model_personalization` 샘플 + 이미 쓰는 MediaPipe blendshapes + TFLM ESP32 포트. 나머지 50%: 표정→의사 라벨 규칙과 신뢰도, 접촉 게이팅, 시간순 누적 평가 하네스, 드리프트 가드. 트리는 단말 재학습이 안 되므로 학생은 작은 선형/1층 MLP로.
- 주말에 먼저: 하드웨어 사지 말고 기존 7시간 로그로 교사-학생 오프라인 시뮬레이션 + 평가 하네스(s8_teacher.py·s8_student.py), 분 요약에 얼굴 검출률·웃음 평균 병기, 모델을 files/에서 읽기.
- 위험한 전제: 3번 — 질문 알림이 모델 출력에 조건화되어 있어 선택 편향·동의 편향·순환 논증. 무작위 팔 B로 반증. (수용, 전제 3 수정.)

## Approaches Considered
- **A. 자기 로그 교사-학생 검증(최소)** — 하드웨어·새 데이터셋 없이 주말 안에 방향 판정. B의 1단계로 흡수됨.
- **B. 온디바이스 자기지도 루프 전체(이상형)** — 선택.
- **C. 비트 동조 지수(창의적)** — 음악으로 좁혀 라벨 없이 가는 길. 영상·SNS 장면을 버리므로 단독 채택 안 함. 1단계 결과가 "좋아한 곡에서만 0~3Hz 증가"로 나오면 두 번째 교사 신호로 흡수.

## Recommended Approach
**B: 온디바이스 자기지도 루프 전체, 단계적으로 (사용자 선택: "B 전체로 바로").** 제 권고는 A→B였으나 사용자는 전체를 한 번에 밀기로 했다. 단, 1단계(=A)가 부정이면 2단계 이후를 재설계한다는 게이트는 유지한다.

**1단계 — 자기 로그로 판정 (제출 직후 주말)**
- 앱: (a) 질문 알림 두 팔(급변 A / 무작위 시각 B, 같은 횟수, 팔 이름을 events.csv `ask` 값에 기록), (b) affect.csv 분 행에 얼굴 검출률·웃음·입벌림 평균·폰 자세(화면 켜짐, 중력축 기준 들고/내려둠) 병기, (c) 모델을 assets가 아니라 files/models/에서 읽기(없으면 assets 기본값) → 재빌드 없이 교체, (d) 학생 모델 형식 = 32개 특징 표준화 + 로지스틱(가중치 텍스트 파일).
- 분석: s8_teacher.py(얼굴 검출된 분에서 smile/jaw → 의사 각성·정서가 라벨 + 신뢰도), s8_student.py(시간순: 앞 날 교사 라벨로 학생 학습 → 뒷 날 격자·맞아요(팔 B)로 평가, 비교군 출하/학생/블렌드, 폰 자세별 분리 평가, 원형 이동 순열검정).
- 게이트: 팔 B에서 학생 또는 블렌드의 within-user AUROC가 출하 모델보다 신뢰구간 하한 기준 높으면 통과. 아니면 교사 규칙·특징을 바꾸거나 C(동조)로 교사 신호를 보강한 뒤 재시도. 두 번 실패하면 KCI 스토리를 "라벨 병목의 정량화"로 재구성.

**2단계 — 단말 안에서 학습 (1단계 통과 후 2주)**
- LiteRT On-Device Training `model_personalization` 샘플을 따라 학생 헤드를 단말에서 재학습·체크포인트 저장. 교사 규칙은 Java로 이식.
- 접촉 게이팅: 화면 켜짐·충전 중·앱 전경·정지 비율로 "폰이 몸에 있나" 판정 → 없으면 추정 보류(K-EmoPhone ScreenEvent·ChargeEvent·AppUsage로 규칙을 먼저 검증).
- 드리프트 가드: 팔 B 일치율이 출하 모델보다 떨어지면 자동 복귀.
- 친구 3~5명 APK(GitHub Releases) 배포, CSV 수동 회수 → n 확장.

**3단계 — 칩셋·경량화 절 (2단계와 병행 가능)**
- 센서 HW FIFO 배치: 가속도 maxReportLatency 1~5분으로 AP 수면, 배치 on/off 전력·웨이크업 수 비교(자이로는 FIFO 없음 → 자이로 없이 가는 근거).
- 실행 계층 비교: Java 트리/로지스틱 vs TFLite int8 CPU vs NNAPI 위임 지연·전력 — 이 크기에선 가속기 오버헤드가 계산보다 크다는 예상.
- 고정소수점 이식: 특징 계산·학생 모델을 int16/int32로 ESP32(TFLM 또는 순수 C)에서 µs·µA 측정. IMU 모듈 손목 로거로 손목 데이터 직접 수집 → "손목 학습 모델을 폰에 썼다"는 한계 해소.
- 외부 데이터: 간호사 E4(32Hz 손목, 일상 스트레스)로 8Hz 상한 한계 보강, DAPPER로 손목 ACC+ESM 재현.

## Open Questions
- 교사 규칙: smile/jaw만으로 각성·정서가 의사 라벨을 만들 때 어느 임계값·어느 신뢰도에서 자를지(1단계에서 격자 탭과 맞춰 정함).
- 폰 자세 판정의 기준(중력축 각도·화면 상태)과 도메인 이동이 크면 교사가 가르친 게 학생에게 전이되는지.
- 무작위 팔의 하루 횟수(피로감 vs 표본): 초안 팔당 2~3회.
- 비트 동조(C)를 넣을지: Android 10 Visualizer 권한·DRM 제약 확인 필요.
- KCI 목표 저널·분량·손목 기기 실험 허용 여부(교수님 확인).
- ESP32 손목 로거의 IMU 선택(MPU-6050 vs ICM-20948)과 샘플링 상한.

## Success Criteria
- 1단계: 팔 B에서 학생/블렌드 within-user AUROC > 출하 모델(부트스트랩 CI 하한 기준), 폰 내려둔 상태에서도 성립. 이게 안 되면 "라벨 병목 정량화"로 전환.
- 2단계: 단말 재학습 1회 < 1초·< 50MB 메모리, 드리프트 가드가 팔 B 일치율 하락을 자동 복귀. 친구 3명 이상 2주 로그 회수.
- 3단계: 배치 on/off 전력 차이와 웨이크업 수 실측 표, 실행 계층 3종 지연·전력 표, ESP32 특징+추정 µs·µA 표.
- 논문: 핵심 주장 "병목은 라벨이고, 단말이 스스로 모은 정답으로만 그 사람 안의 변화를 읽게 된다"를 1~3단계 실측이 받침.
