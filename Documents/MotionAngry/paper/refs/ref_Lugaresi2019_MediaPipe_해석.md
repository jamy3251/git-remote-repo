## 한 줄 요약

MediaPipe는 모델 추론·영상 처리·데이터 변환 같은 구성 요소(계산기)를 방향 그래프로 연결해 음성·영상 등 시계열 감각 데이터를 실시간으로 처리하는 지각 파이프라인을 만들고, 같은 그래프를 데스크톱과 모바일에서 동일하게 실행하며, 추적기·시각화 도구로 성능을 측정하게 해 주는 범용 프레임워크를 제안한 논문이다.

## 논문이 설명하는 것

### 문제 정의와 설계 목적

지각(perception) 응용을 만들려면 (a) 알고리즘·모델 선택과 개발, (b) 프로토타입·데모 제작, (c) 자원 소비와 품질 간 균형, (d) 문제 사례 식별과 완화를 모두 거쳐야 한다. 처리 단계 사이의 과도한 결합 때문에 단계를 추가하거나 모델을 바꾸기 어렵고, 플랫폼별로 같은 응용을 다시 최적화하는 데 시간이 든다. MediaPipe는 개별 모델과 처리 단계를 공통 인터페이스(시계열 데이터 지향)로 추상화해 재사용 가능한 파이프라인으로 연결하고, 워크스테이션에서 개발한 그래프를 그대로 모바일에 배포할 수 있게 하는 것을 목적으로 한다. 주 사용자는 연구자·학생·개발자 등 ML 실무자이며, 핵심 용도는 추론 모델과 재사용 구성 요소로 지각 파이프라인을 빠르게 프로토타이핑하는 것이다.

프레임워크는 세 부분으로 이루어진다. (a) 감각 데이터 추론용 프레임워크, (b) 성능 평가 도구, (c) 재사용 가능한 추론·처리 구성 요소(계산기) 모음.

### 관련 연구와의 차이

TensorFlow·PyTorch 같은 신경망 엔진의 그래프는 노드가 단순하고 결정적(입력 하나에 출력 하나)이지만, MediaPipe의 노드는 입력 하나에 출력 0개·1개·여러 개를 낼 수 있어 더 높은 수준의 동적 동작을 표현한다. Beam·Dataflow는 클러스터 배치 처리용이라 스트리밍 음성·영상에 맞지 않고, ROS는 노드가 프로세스여서 IPC 오버헤드가 있으며, GStreamer는 분석보다 미디어 편집에 치우쳐 있고, OpenCV G-API는 이미지 연산 시퀀스에 한정된다는 점을 들어 차별화한다.

### 구조: 패킷, 스트림, 사이드 패킷, 계산기, 그래프

- 패킷(Packet): 기본 데이터 단위. 숫자 타임스탬프와 불변(immutable) 페이로드에 대한 공유 포인터로 이루어진다. 페이로드는 임의의 C++ 타입이며, 패킷은 값처럼 싸게 복사되고 복사본끼리 참조 계수로 소유권을 공유한다.
- 스트림(Stream): 노드와 노드를 잇는 연결로, 타임스탬프가 단조 증가하는 패킷의 열을 운반한다. 출력 스트림 하나를 같은 타입의 입력 스트림 여러 개에 연결할 수 있고, 각 입력은 자기 큐를 가져 소비 속도를 따로 가진다.
- 사이드 패킷(Side packet): 타임스탬프가 없는 단일 패킷 연결로, 모델 파일 경로처럼 실행 중 변하지 않는 값을 넘기는 데 쓴다.
- 계산기(Calculator): 그래프의 노드 구현체. 입력 스트림·사이드 패킷을 0개 이상 받아 출력 스트림·사이드 패킷을 0개 이상 낸다. 모두 같은 기반 클래스에서 파생하며 GetContract()(입출력 타입 선언), Open()(실행 시작 시 상태 준비), Process()(입력이 들어올 때마다 반복 호출), Close()(종료 처리) 네 메서드로 구성된다. 각 계산기는 기본적으로 한 번에 한 스레드에서만 실행되고 패킷이 불변이므로, 멀티스레드 전문 지식 없이도 사용자 정의 계산기를 쓸 수 있다.
- 그래프(Graph)와 GraphConfig: 파이프라인은 GraphConfig 프로토콜 버퍼로 토폴로지와 노드 옵션을 기술하고 Graph 객체로 실행한다. 초기화 때 (1) 모든 스트림·사이드 패킷의 생산자가 하나인지, (2) 연결된 입출력 타입이 맞는지, (3) 각 노드의 연결이 계약과 맞는지 검사한다. 데이터는 소스 노드(입력 없이 패킷을 스스로 생성) 또는 그래프 입력 스트림(응용이 카메라 텍스처 등을 밀어 넣음)에서 출발하고, 싱크 노드·콜백·출력 스트림 폴링으로 빠져나간다. 서브그래프(Subgraph)로 그래프 일부를 모듈화해 계산기처럼 재사용할 수 있으며, 로드 시 원래 계산기 그래프로 치환되므로 성능 차이가 없다. 그래프 수준 설정(실행기, 스레드 수, 입력 큐 최대 크기)으로 데스크톱과 모바일에 맞게 조정할 수 있고, 모바일에서는 무거운 추론 계산기를 별도 실행기에 붙이면 스레드 지역성 덕에 실시간 성능이 좋아진다고 설명한다.

### 구현: 스케줄링, 동기화, 입력 정책, 흐름 제어

- 스케줄링: 그래프마다 하나 이상의 스케줄러 큐(우선순위 큐)가 있고 큐마다 실행기(executor) 하나가 붙는다. 노드는 "준비 안 됨, 준비됨, 실행 중" 상태를 가지며, 준비 여부 함수가 초기화 시·노드 종료 시·입력 상태 변화 시 호출된다. 초기화 때 위상 정렬로 우선순위를 매겨 출력 쪽에 가까운 노드가 높은 우선순위를, 소스 노드가 가장 낮은 우선순위를 받는다.
- 동기화: 전역 시계가 없는 분산 실행이라 서로 다른 노드가 다른 타임스탬프의 데이터를 동시에 처리할 수 있어 파이프라이닝 처리량이 높다. 대신 타임스탬프를 동기화 키로 삼아 여러 입력 스트림을 맞춘다. 각 스트림에는 타임스탬프 하한(timestamp bound)이 있어 타임스탬프 T의 패킷이 오면 하한이 T+1로 올라가고, 그 아래로는 더 이상 패킷이 오지 않음이 확정된다.
- 기본 입력 정책: 같은 타임스탬프의 패킷은 실시간 도착 순서와 무관하게 항상 함께 처리되고, 입력 집합은 엄격한 타임스탬프 오름차순으로 처리되며, 패킷이 버려지지 않아 완전히 결정적이고, 이 보장을 지키는 한 가장 빨리 준비된다. "정착된(settled) 타임스탬프"(하한보다 작아 패킷 유무가 확정된 시각) 개념으로 준비 조건을 정의한다. 필요하면 노드별로 다른 정책(즉시 수신, 입력 집합 분리)을 선택할 수 있다.
- 흐름 제어: 생산 속도가 처리 속도보다 빠를 때를 위해 두 장치가 있다. 백프레셔(스트림 버퍼가 한도에 닿으면 상류 노드를 늦춤, 결정성 유지, 데드락 회피 포함)와 패킷을 떨어뜨리는 특수 노드(흐름 제한기)이다. 서브그래프 입구에 흐름 제한기를 두고 최종 출력에서 되돌리는 루프백을 연결하면 하류에서 처리 중인 타임스탬프 수를 세어 상류에서 미리 패킷을 버리므로, 중간까지 처리하고 버리는 낭비가 없다.

### GPU 지원

GPU 계산·렌더링 노드를 CPU 노드와 섞어 쓸 수 있다. OpenGL ES(Android 3.2까지, iOS 3.0까지), Metal(iOS)을 지원하되 단일 교차 API 추상화를 두지 않고 노드마다 플랫폼 API를 직접 쓰게 한다. GPU 데이터는 불투명 버퍼 타입으로 표현하고 노드가 필요할 때 API별 뷰(예: OpenGL 텍스처)를 잠시 얻는다. 느린 추론 경로(예: 10 FPS)와 빠른 렌더링 경로(예: 30 FPS)를 서로 다른 GL 컨텍스트에서 돌리고, 컨텍스트마다 전용 스레드를 두며, 버퍼마다 생산자 펜스 하나와 소비자 펜스 여러 개를 자동 삽입해 CPU 동기화 없이 GPU 명령 스트림 안에서 교차 컨텍스트 동기화를 처리한다.

### 성능 도구

- 추적기(Tracer): 패킷이 그래프를 지나는 동안 이벤트 시각, 패킷 타임스탬프, 패킷 데이터 ID, 노드 ID, 스트림 ID를 담은 TraceEvent를 기록하고, 계산기별·스트림별 CPU 시간 히스토그램을 낸다. 실시간 지연, 패킷 버퍼링에 따른 메모리 누적, 프레임률이 다른 스트림의 결합 문제를 진단하고 임계 경로를 찾는 데 쓴다. GraphConfig로 켜고 컴파일 플래그로 완전히 뺄 수 있으며, 뮤텍스 없는 스레드 안전 원형 버퍼로 측정 영향을 최소화한다.
- 시각화 도구(Visualizer): 타임라인 뷰(스레드별 패킷 타이밍)와 그래프 뷰(추적 파일에서 추론한 토폴로지, 각 계산기 상태와 입력 큐의 패킷)를 제공한다.

### 예제 파이프라인

- 객체 탐지(6.1절, 그림 1): 매 프레임 탐지는 비용이 크므로, 느린 탐지 분지(프레임 선택 노드가 빈도 제한 또는 장면 변화로 일부 프레임만 탐지기에 넘김)와 빠른 추적 분지(이전 탐지를 현재 프레임으로 전진)를 병렬 실행기로 돌린다. 탐지 병합 노드는 기본 입력 정책 덕에 새 탐지와 추적 결과를 같은 프레임 타임스탬프에 맞춰 합치고, 주석 노드가 카메라 프레임과 자동 동기화해 몇 프레임 늦지만 완벽히 정렬된 뷰파인더를 출력한다. 모델 파일과 레이블 맵은 사이드 패킷으로 들어간다. 무거운 신경망 탐지기를 가벼운 템플릿 매칭 탐지기로 바꿔도 나머지 그래프는 그대로다.
- 얼굴 랜드마크 탐지와 인물 분할(6.2절, 그림 5·6): 두 작업을 동시에 돌리는 부담을 줄이기 위해 역다중화(demultiplexing) 노드로 입력 프레임을 교대로 두 출력 스트림에 나눠 넣고, 랜드마크와 마스크를 시간 보간해 모든 프레임에 대응시킨 뒤 주석 노드에서 세 스트림을 입력 정책으로 동기화해 겹쳐 그린다. 얼굴 랜드마크 노드를 GPU 추론 엔진 기반 구현으로 바꾸면 GPU에서 CPU로의 데이터 전송 병목 없이 끝까지 GPU에서 처리할 수 있다. 이 절에서 다루는 것은 "얼굴 랜드마크 탐지 그래프"라는 파이프라인 구성 예시이며, 랜드마크 모델의 구조·정확도나 표정 계수(blendshape)는 등장하지 않는다.

## 주요 주장

1. 지각 파이프라인을 재사용 가능한 계산기의 방향 그래프로 기술하면 단계 추가·교체가 쉬워지고, 같은 그래프를 데스크톱에서 개발한 뒤 모바일로 배포할 수 있다.
2. 타임스탬프를 동기화 키로 쓰는 기본 입력 정책은 결정적(패킷 손실 없음, 도착 순서 무관)이면서 실시간 제약을 위해 필요한 곳에서만 결정성을 완화할 수 있다.
3. 흐름 제한기와 백프레셔로 자원 사용을 통제하고, 다중 GL 컨텍스트와 자동 펜스 삽입으로 GPU 경로를 효율적으로 섞을 수 있다.
4. 추적기·시각화 도구로 기기별 지연과 자원 소비를 재현 가능하게 측정할 수 있다.
5. Google 내부에서 6년 이상 사용되었고 성공의 주된 이유는 재사용 가능한 계산기·그래프 생태계라고 밝힌다.

## 한계

- 정량 평가가 없다. 지연·FPS·메모리 수치, 다른 프레임워크와의 비교 실험이 전혀 제시되지 않고, "실시간", "효율적", "immensely successful" 같은 서술은 저자 주장에 머문다. 논문 자체가 시스템 설명서 성격의 arXiv 기술 보고서이며 동료 심사를 거친 게재본이 아니다.
- 모델 자체(얼굴 랜드마크, 객체 탐지 모델의 구조·학습·정확도)는 범위 밖이다. 이 논문을 인용해 어떤 모델의 정확도나 출력 형식을 뒷받침할 수 없다.
- 2019년 v1 시점의 설계를 기술한다. 이후 MediaPipe Solutions·Tasks API(Face Landmarker 등), Python·Web·Android Tasks 라이브러리, blendshape 출력은 이 논문 이후에 추가된 것으로 논문에 없다.
- GPU 설명은 Android OpenGL ES 중심이고 Vulkan은 언급만 한다.
- 결정성과 실시간성의 상충을 입력 정책 변경으로 푼다고 했지만, 특수 입력 정책을 쓰는 계산기는 다른 계산기와 임의로 섞을 수 없다는 제약(각주 3)을 스스로 인정한다.

## 우리 연구와의 연결

우리는 일상 기록 모드에서 앞카메라 프레임을 초당 2장 MediaPipe Face Landmarker(Android `com.google.mediapipe:tasks-vision:0.10.35`, `FaceRecorder.java`)에 넣어 표정 계수(blendshape) 52개만 CSV로 저장하고 영상·얼굴 이미지는 저장하지 않는다. 이 논문이 우리 연구에 기여하는 지점은 "폰 안에서 카메라 입력을 실시간 지각 파이프라인으로 처리하는 프레임워크"라는 사실뿐이다. 패킷 불변성·단일 스레드 계산기·흐름 제한기 같은 설계는 우리가 Face Landmarker를 초당 2장으로 호출하는 상위 코드에서 직접 쓰지 않으며, 우리는 Tasks API가 내부 그래프를 감싼 결과만 받는다.

인용 범위에 대한 판단은 다음과 같다. 이 논문은 프레임워크(그래프·계산기·패킷·스트림·스케줄러·도구)만 다루며, Face Landmarker, 468/478점 얼굴 메시, blendshape 52개는 어디에도 나오지 않는다. 6.2절의 "얼굴 랜드마크 탐지" 예제도 그래프 구성 예시일 뿐 모델이나 출력 형식을 정의하지 않는다. 따라서 본문에서 이 논문[10]을 달 때는 "MediaPipe 프레임워크" 또는 "MediaPipe 프레임워크 위의 얼굴 분석 모델"로 프레임워크만 가리키는 것이 정확하다. 현재 원고(`paper/main_ko.md` 74행, 표 67행)처럼 "MediaPipe Face Landmarker[10]"라고 쓰면 이 논문이 Face Landmarker를 기술하는 것으로 읽혀 부정확하다. "MediaPipe[10] 기반 Face Landmarker 0.10.35" 또는 "MediaPipe 프레임워크[10]의 Face Landmarker 태스크(버전 0.10.35)"처럼 프레임워크 인용과 구체 도구 명칭을 분리해 적는 것이 맞다.

blendshape 52개의 출처는 별도 근거가 필요하다. Face Landmarker의 52개 계수는 Apple ARKit의 ARFaceAnchor blendshape 위치 52개와 호환되도록 학습된 별도 모델(face_blendshapes)의 출력이며, 이 논문에는 그 사실이 없다. 따라서 (1) blendshape 모델 자체는 Google의 MediaPipe Face Landmarker 모델 카드 또는 Tasks 공식 문서(접근 일자 표기)로, (2) 52개 계수의 정의와 의미는 Apple ARKit 문서나 ARKit blendshape를 다룬 문헌(`paper/refs/ref_Aldenhoven2026_ARKit.pdf` 참고)으로 각각 인용하는 것이 안전하다. 이 논문 하나로 "blendshape 52개"를 뒷받침하면 근거 없는 인용이 된다.

또 한 가지, 우리 연구에서 중요한 "영상을 저장하지 않고 계수만 남긴다"는 프라이버시 설계는 MediaPipe의 기능이 아니라 우리 앱(`FaceRecorder.java`)의 선택이다. 이 논문을 프라이버시 근거로 인용하면 안 된다.

## 인용 시 주의점

- 서지 형식: C. Lugaresi, J. Tang, H. Nash, C. McClanahan, E. Uboweja, M. Hays, F. Zhang, C.-L. Chang, M. G. Yong, J. Lee, W.-T. Chang, W. Hua, M. Georg, and M. Grundmann, "MediaPipe: A framework for building perception pipelines," arXiv preprint arXiv:1906.08172, 2019. 저자가 14명이므로 "C. Lugaresi et al."로 줄여도 되지만 참고문헌에는 arXiv 프리프린트임을 밝힌다.
- 이 논문으로 뒷받침할 수 있는 문장: "MediaPipe는 모바일을 포함한 여러 플랫폼에서 카메라 입력을 실시간으로 처리하는 지각 파이프라인 프레임워크다." 정도까지다.
- 이 논문으로 뒷받침할 수 없는 문장: Face Landmarker의 존재·버전·정확도, 478점 메시, blendshape 52개, ARKit 호환성, 초당 처리 속도 수치, 프라이버시 보장, 온디바이스 학습.
- 논문에 정량 벤치마크가 없으므로 "MediaPipe는 X ms 안에 처리한다"류의 수치를 이 논문에 귀속시키지 않는다. 우리 기기에서 측정한 수치는 우리 결과로 적는다.
- 논문은 Google 내부 사용과 공개 예정 저장소를 언급하므로, 2019년 이후 API 변화(Solutions, Tasks)는 공식 문서를 접근 일자와 함께 따로 인용한다.
