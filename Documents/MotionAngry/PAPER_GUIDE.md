## 2. 양식

IAAI 2026 한국어 학회 양식이다. 아래 값은 제출한 docx에서 직접 읽은 것이다.

### 2.1 페이지와 글꼴

| 항목 | 값 |
|---|---|
| 분량 | 4쪽 (약물재배치 논문은 5쪽 이내로 냈고, MotionAngry는 4쪽에 맞춤) |
| 용지 | Letter (8.5 × 11 in) |
| 여백 | 상하좌우 0.65 in |
| 단 | 1단 |
| 본문 | 맑은 고딕 9pt, 첫 줄 들여쓰기 |
| 국문 제목 | 15pt 굵게, 가운데 |
| 영문 제목 | Heading 1 스타일 |
| 장 제목 (I. 서론 등) | Heading 1, 맑은 고딕 14pt 굵게 |
| 절 제목 (3.1) | Heading 2, 13pt 굵게 |
| 항 제목 (3.1.1) | Heading 3, 굵게 |
| 표·그림 캡션 | 8pt 굵게, 가운데. **표 캡션은 표 위, 그림 캡션은 그림 아래** |
| 표 안 글씨 | 8pt, 첫 행 굵게, Table Grid |
| 참고문헌 | 8pt |

분량 감: 본문 약 9,700자 + 표 4~5개 + 그림 2~3개가 4쪽이었다.

### 2.2 순서와 구성

```
국문 제목
영문 제목
저자 (국문) / 저자 (영문) / 이메일
*소속, 전공심화  (**소속, 교수(교신저자))
Abstract  (영문, 한 단락)
Keywords: 영문 키워드 5개

I. 서론
II. 관련 연구          (2.1, 2.2 두 절이거나 절 없이 한두 단락)
III. 시스템 설계 및 구현
   3.1 시스템 설계
      3.1.1 개발 환경      → 표 1. 개발 환경 (구분 / 항목 / 버전)
      3.1.2 시스템 구성    → 그림 1. 시스템 구성도 (흐름도)
      3.1.3 (핵심 설계 요소: 판별 조건, 정보 수준 정의 등)
   3.2 (핵심 알고리즘 또는 실험 및 검증 방법)
   3.3 구현 결과
      3.3.1 ~ 3.3.n (결과별 단락)
IV. 결론               (결과 요약 → 한계 → 핵심 결론 → 향후 계획)
참고문헌
```

- 실험 결과를 따로 "V. 실험" 장으로 빼지 않는다. 결과는 3.3 구현 결과에, 정리는 IV. 결론에 넣는다.
- 그림 1은 시스템 구성도로 새로 그린다. 구현한 부분은 실선, 향후 과제는 점선으로 구분할 수 있다.
- 표·그림은 본문에서 먼저 "표 2는 ~이다", "그림 1과 같이"로 언급한 뒤 배치한다.

### 2.3 참고문헌

- IEEE 형식: `[1] R. Wang et al., "제목," in Proc. ACM UbiComp, pp. 3–14, 2014.`
- 국내 보고서: `[1] 한국과학기술정보연구원, 「ASTI Market Insight 135: AI 신약개발」, 2023.`
- 본문 인용은 문장 끝 `[1]` 또는 `[1,2]`.
- 저자 이름과 서지 정보는 직접 검색해서 확인한 뒤 채운다. 저자에게 "참고문헌 저자 확인해 주세요"라고 넘기지 않는다.
- 4쪽 논문은 8~10편이면 충분하다.

## 3. 저자가 직접 준 피드백

### 3.1 MotionAngry 초안 v1을 읽고 (2026-10-20)

저자 원문:

> 제목 이상한 말 쓰지말고 그냥 기술 논문 제목처럼 해주고, abstract 살짝 요약 그리고 보면 무슨 emophone 얘기만 계속 하는데 이 연구가 밝히는것은 뭔지, 의의가 뭔지 어떤 의미를 가지는지, 어떤 실험과 검증의 과정을 거쳤는지, 그리고 표의 가속도나 이런게 어떤 의미인지도 너무 모르겠어. 다른 논문 참고, 참조하는건 좋은데 우리 논문에 너무 그런식으로 도배가 되버리면 안될것 같아. 그리고 구현결과의 단락들도 단락 느낌으로 해야지 메세지 위주로 나누니까 이상하잖아. 한계도 서술하지만 그 속에서 얻어낸 기막힌 결론.

반영 규칙:

1. **제목은 평범한 기술 논문 제목으로 쓴다.** 수사적 질문, 부제, 멋 부린 표현을 쓰지 않는다.
   - 나쁨: "움직임 신호의 정서 정보는 어디에 있는가: 실험실·일상 데이터 비교와 온디바이스 구현"
   - 좋음: "모바일 모션 센서 기반 온디바이스 정서 추정 시스템의 설계 및 구현"
   - 좋음: "AI 기반 약물재배치 가설 생성 시스템 개발"
2. **초록은 짧게 요약한다.** 한 단락으로 무엇을 만들었고, 어떻게 검증했고, 무엇을 밝혔는지만 쓴다.
3. **남의 데이터셋·논문으로 본문을 도배하지 않는다.** 데이터셋 이름은 방법에서 한 번 소개하고, 이후에는 "실험실 데이터", "일상 데이터"처럼 역할로 부른다. 중심은 항상 이 연구다.
4. **이 연구가 밝힌 것, 의의, 거친 실험·검증 과정을 중심으로 쓴다.** 검증 단계를 표로 정리하면 좋다 (예: 표 2. 검증 단계 구성: 1단계 공개 데이터 분석 → 2단계 단말 실행 → 3단계 실사용 파일럿).
5. **표에 나오는 지표와 특징이 무슨 뜻인지 본문에서 쉽게 풀어 준다.** AUROC, Hz, 저크, 주파수 대역, 가속도 세기 등은 처음 나올 때 한 줄로 설명한다.
   - 예: "AUROC는 두 상태를 얼마나 잘 구분하는지를 나타내며 0.5는 우연 수준이다."
   - 예: "정서가(기분이 좋은지), 각성(얼마나 들떠 있는지)"
   - 캡션에도 읽는 법을 넣는다: "표 3. ... (AUROC, 0.5=우연; –: 해당 데이터에 없음)"
6. **결과 소제목은 단락형으로 단다.** 결론 문장을 소제목으로 쓰지 않는다.
   - 나쁨: "3.3.1 OS 활동 범주로는 일상 정서를 추정할 수 없다"
   - 좋음: "3.3.1 움직임 정보 수준별 정서 추정 성능", "3.3.2 움직임 강도 통제 실험", "3.3.3 단말 실행 성능"
7. **한계를 쓰고, 그 한계들을 묶어 강한 핵심 결론을 낸다.** 결론 장은 "본 연구에는 한계가 있다. ..."로 한계를 나열한 뒤 "그러나 이 한계들을 함께 놓으면 하나의 일관된 결론이 드러난다. ..."로 이어서, 결과 전체를 꿰는 한 문장짜리 통찰로 끝낸다.

### 3.2 MotionAngry 진행 중 (2026-10-03 ~ 10-13)

8. **하지 않은 실험을 한 것처럼 쓰지 않는다.** 초안에 실험을 이미 마친 것처럼 적었다가 지적받았다("우리가 이미 실험한거 처럼 되어있던데 뭐야"). 아직 안 한 일은 수치를 지어내지 말고, 작성 중에는 【미완】 같은 표시를 붙인다. 제출본에서는 표시를 지우고 "향후 과제"나 "한계" 문장으로 바꾼다. 측정에 실패한 항목(예: 통제 실패로 비교할 수 없게 된 배터리 측정)은 수치를 쓰지 않는다.
9. **주제를 한 분야에 가두지 않는다.** "소비자 심리" 하나에 묶지 말고 여러 분야 활용, 검증 용이성, IT 시스템 통합을 우선한다.
10. **저자가 원하는 연구 목표를 놓치지 않는다.** 저자가 "그래서 우리가 정확히 뭘 검증하고 뭘 만들고 있는거야?"라고 물은 적이 있다. 저자가 원한 것은 "콘텐츠 시청 중 실시간 감정 피드백"이었는데, 보조 실험(배터리 소모 측정)이 메인처럼 진행되고 있었다. 실험을 설계하기 전에 "무엇을 만들고, 무엇을 검증하고, 그것이 어떤 목표에 기여하는지"를 한 문단으로 먼저 확인받는다. 보조 실험은 짧게 끝낸다.
11. **데이터 수집은 최대한 포괄적으로 한다.** "폰을 꺼낼 때만 측정" 같은 조건부 수집을 제안하지 않는다. 저자 원칙은 모든 상황 상시 기록이다.
12. **저자가 아이디어를 더하면 받아서 확장한다.** 예: 표정 인식을 넣어 피드백을 다시 반영하자는 제안은 실시간 정답 신호로 설계에 넣었다.

### 3.3 약물재배치 논문 (2026-05)

13. **초록은 한 단락으로 쓴다.**
14. **서론은 세 흐름으로 쓴다.** 배경·문제(왜 중요한가) → 기존 연구의 한계 → 본 논문이 한 일.
15. **문장은 짧게 쓴다.**
16. **관련 연구는 두 절 이내로 쓴다.**
17. **설계 설명은 하나의 흐름으로 이어 쓴다.** 조건이나 규칙을 잘게 나눈 목록으로 쓰지 않는다.
18. **핵심 알고리즘 하나를 독립 절로 깊게 쓴다.** 단계마다 절을 따로 만들지 않고, 가장 중요한 하나를 "3.2 MCTS 기반 기전 경로 탐색"처럼 쓴다. 다른 단계는 3.1.2 시스템 구성에서 한 단락으로 소개한다.
19. **실험과 결론을 IV. 결론으로 통합한다.**
20. **저자가 되돌린 내용을 존중한다.** 저자가 직접 고친 부분(삭제했던 Stage 설명 복원 등)은 다시 지우지 않는다.
21. **사실 오류와 잔재를 남기지 않는다.** 실제로 쓴 라이브러리와 표 내용이 맞는지, 다른 프로젝트에서 복사한 문장이 남아 있지 않은지, 오타("신신약")가 없는지 확인한다.

## 4. 문체

최종본 두 편에서 공통으로 쓴 문체다.

- 평서 과거형: "~을 구현하였다", "~로 나타났다", "~을 확인하였다".
- 주어: "본 논문은", "본 연구는", "제안한 시스템은".
- 쉬운 우리말을 쓴다. 전문 용어는 처음 나올 때 풀어 쓴다 (예: "운영체제(OS)", "결정트리 모델(LightGBM[5])").
- 수치는 해석과 함께 쓴다. "0.60이었다"로 끝내지 말고 무엇보다 얼마나 나은지, 무슨 뜻인지 붙인다.
- 과장하지 않는다. 주장은 데이터가 보여 주는 범위 안에서만 한다. 예: "특정 약물이 치료 효과를 가진다는 결론을 내리는 도구가 아니라 ... 보조 도구로 이해해야 한다."
- 강조 굵게는 표 안의 최고값 정도로만 쓴다.
- 이모지와 AI가 쓴 티가 나는 표현을 쓰지 않는다 (불필요한 영어 병기, "혁신적인", "획기적인", 화살표 나열 등).
- 파일럿이나 소표본 결과는 "절차 확인", "가설 수준"으로 낮춰 쓰고, 보정 후 유의하지 않으면 그대로 적는다.

## 5. 작업 방식

1. **장마다 초안 → 저자 확인.** 긴 설명판(main_ko.md)과 제출용 docx를 따로 둔다. docx는 스크립트로 생성해서 수치가 바뀌면 다시 돌린다.
2. **docx는 지난 논문 파일을 템플릿으로 만든다.** 이전 IAAI docx를 python-docx로 열고 본문만 지운 뒤 다시 채우면 스타일·여백이 그대로 유지된다. 참고: `D:\Projects\Documents\MotionAngry\src\build_paper_docx.py`.
3. **쪽수는 저자에게 확인받는다.** 이 PC에는 Word와 LibreOffice가 없고, 한컴오피스 COM 자동화는 보안 확인 창에서 멈춘다. 분량을 추정한 뒤 "한글로 열어서 몇 쪽인지 알려 주세요"라고 요청한다.
4. **저자가 파일을 열어 둔 상태면 덮어쓰지 못한다.** `_v2`처럼 새 이름으로 저장하고 알려 준다.
5. **제출 전 확인 목록을 준다.** 학회 공지(분량·파일 형식·마감), 그림 글씨가 인쇄 크기에서 읽히는지, 한계 문단과 주장 범위가 맞는지.
